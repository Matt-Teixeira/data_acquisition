Dockerized Postgres on Azure VM — Build Runbook & Connection Guide

Revision 3. Merges the VM setup doc, the SSL config doc, and the developer connection guide into a single source of truth. Supersedes all three.

This document describes the target state, not necessarily what is currently deployed. Existing hosts predate some of these corrections — see Known Divergences before auditing a running server and concluding something is broken.

01BUILD RUNBOOK

Context

Self-managed Dockerized Postgres 16 on an Azure VM. Developers share /opt resources via docker group membership. Postgres runs as UID 999 inside the container. TLS is mandatory; unencrypted connections are rejected by the server.

Security property, stated rather than assumed: the container's pg_hba.conf retains local and loopback trust rules. Combined with shared docker group membership, any developer in the docker group has passwordless superuser access to the database via docker exec. That is inherent — the docker group is root-equivalent regardless — but it should be a known property of the design, not a surprise discovered later.

Confirm which tenant your shell is pointed at

Each environment is a separate Entra tenant, so the same az command will hit a different environment depending on which tenant your session is authenticated to. Commands in this document are written as plain az — what matters is that the shell is pointed at the right place before you run them:

azure-cli
$az account show --query "{sub:name, tenant:tenantId, user:user.name}" -o table

Compare that against the table above. Either way of getting there is fine:

  • az login --tenant <TENANT_ID> — straightforward, but replaces your token cache, so you re-authenticate when switching back.
  • azenv <env> — an internal wrapper that opens a subshell with an isolated token cache per environment, so plain az inside it targets that environment and your other sessions survive. Optional; see Appendix A.

00Confirm Which Host You Are On

Every environment has its own certificate, its own public IP, and its own NSG. Hostnames are frequently identical across environments when VMs come from the same template, so hostname proves nothing.

curl
$curl -s -H Metadata:true \
  "http://169.254.169.254/metadata/instance/compute?api-version=2021-02-01&format=json" \
  | python3 -c 'import sys,json;d=json.load(sys.stdin);print(d["name"],d["resourceGroupName"],d["location"])'
 
$curl -s -H Metadata:true \
  "http://169.254.169.254/metadata/instance/network/interface/0/ipv4/ipAddress/0/publicIpAddress?api-version=2021-02-01&format=text"

Record that public IP. It goes into the certificate SAN in Step 4, and a certificate carrying another host's IP will fail verification for every external client.

Verify the disk layout — do not assume it

Device letters shuffle between builds, and /mnt is the Azure ephemeral resource disk, which is wiped on deallocate.

docker
$docker info --format '{{.DockerRootDir}}'   # after Docker is installed
$findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS /
$lsblk -o NAME,SIZE,MOUNTPOINT,UUID
$grep -v '^#' /etc/fstab                     # data disks mounted by UUID/PARTUUID

Decide deliberately where postgres_data will live. Docker's default data-root is /var/lib/docker on the OS disk; moving it after go-live means downtime plus a full copy. If it belongs on a managed data disk, set data-root in /etc/docker/daemon.json before Step 3.

02Create Users

Developer accounts

shell
$sudo adduser <username>
$sudo usermod -aG docker <username>

Group membership takes effect on next login. If you added yourself to docker in your current session, start a new one (newgrp docker, or log out and back in) before docker run hello-world will work without sudo.

source ~/.bashrc does not help here, despite being the usual fix for shell config changes. Supplementary group membership is a property of the process, assigned by the login process at session start and inherited by every child. Sourcing a file only re-reads shell configuration — it cannot change the groups the current shell already has. Confirm with id: docker will still be absent. newgrp docker works because it starts a new shell with the group applied.

docker
$docker run hello-world

Service account

shell
$sudo adduser \
  --system \
  --no-create-home \
  --group \
  --shell /usr/sbin/nologin \
  svc

System users are allocated UIDs counting down from 999 on Debian/Ubuntu. This matters: the container's Postgres user is UID 999, and whichever host package creates a system user first may claim it. See Understanding UID 999 below.

03Shared Resource Permissions

Run once per VM, by an admin.

shell
# Shared directories, setgid so new files inherit the docker group
$for d in /opt/run-logs /opt/apps /opt/resources; do
$  sudo mkdir -p "$d"
$  sudo chgrp docker "$d"
$  sudo chmod 2775 "$d"
$done
 
# Default ACLs so files created by any dev remain group-accessible
$for d in /opt/run-logs /opt/apps /opt/resources; do
$  sudo setfacl -d -m g:docker:rwX "$d"
$  sudo setfacl -m  g:docker:rwX "$d"
$done

The 2 in 2775 is setgid: files created inside inherit the docker group rather than the creator's primary group. The default ACL (-d) does the same for ACL entries, so a file created by one developer stays writable by the others.

Consequence to be aware of: every file created under /opt/resources inherits group:docker:rwx. Any docker group member can overwrite any file there, including certificates. That is intended for shared development, but it means /opt/resources is not a place to store anything only one person should modify.

Check the umask

shell
$umask

Step 4 relies on 022 (files created 644). If these hosts use 027, certificates will land at 640 and you must chmod 644 the certificate explicitly after every regeneration.

04Generate the Certificate

Run as your developer user — no sudo needed.

shell
$mkdir -p /opt/resources/ssl
 
$openssl genrsa -out /opt/resources/ssl/pg_ssl.key 2048
 
$openssl req -new -x509 -days 1095 \
  -key /opt/resources/ssl/pg_ssl.key \
  -out /opt/resources/ssl/pg_ssl.crt \
  -subj "/CN=pg_db" \
  -addext "subjectAltName=DNS:pg_db,DNS:postgres-server,DNS:localhost,IP:<THIS_VM_PUBLIC_IP>,IP:127.0.0.1"

Verify immediately, before wiring anything up:

openssl
$openssl x509 -in /opt/resources/ssl/pg_ssl.crt \
  -noout -dates -ext subjectAltName -fingerprint -sha256

The IP in the SAN must equal the IP recorded in Step 0. Record the fingerprint — it is what developers use to confirm they hold the right certificate.

Why every SAN entry is there

The subjectAltName must cover every hostname and IP that clients will use. Node and modern TLS clients reject mismatches with ERR_TLS_CERT_ALTNAME_INVALID.

Entry Covers
DNS:pg_db Docker container name — dockerized apps on pg_net
DNS:postgres-server Legacy CN, retained for compatibility; also the name verified when connecting via the host + hostaddr form
DNS:localhost DB IDEs that internally proxy connections through localhost
IP:<VM_PUBLIC_IP> External clients, App Service, direct psql
IP:127.0.0.1 Loopback equivalent of localhost

Pin a static public IP, and if a DNS name exists — even the Azure *.cloudapp.azure.com FQDN — put it in the SAN so the certificate outlives the address. Every IP change otherwise forces a regeneration and a redistribution to every developer and deployment.

Comparing certificates across hosts

To prove two hosts have genuinely separate keypairs, rather than one certificate copied across — which produces a stale SAN and silent client failures:

shell
$cd /opt/resources/ssl && { hostname; \
  openssl x509 -in pg_ssl.crt -noout -dates -ext subjectAltName -fingerprint -sha256; \
  echo -n "modulus: "; openssl x509 -in pg_ssl.crt -noout -modulus | openssl sha256; }

Different fingerprints prove different certificates. Different moduli prove different private keys.

05Set Certificate Permissions

shell
# Certificate is PUBLIC — world-readable, no ACL needed
$chmod 644 /opt/resources/ssl/pg_ssl.crt
 
# Key: transfer ownership to UID 999 (postgres inside the container)
$sudo chown 999:docker /opt/resources/ssl/pg_ssl.key
$sudo setfacl -b /opt/resources/ssl/pg_ssl.key
$sudo chmod 600 /opt/resources/ssl/pg_ssl.key

Final state

output
pg_ssl.crt  →  644, owned by $USER:docker            ✓
pg_ssl.key  →  600, owned by 999:docker, no ACL      ✓

Why the certificate is 644 and not ACL-protected

pg_ssl.crt is a public certificate. It is handed to every developer, bundled into App Service deployments, and served to anyone who opens a TCP connection to 5432 — openssl s_client retrieves it without authenticating. Guarding it achieves nothing while costing a great deal:

  • An ACL entry is silently lost whenever the file is overwritten, so every regeneration must remember to re-apply it or the container fails to read the certificate on next restart. other::r-- is not subject to the ACL mask and survives the default ACL inheritance from /opt/resources, which is what makes 644 durable where an ACL is not. It also guarantees readability for application containers, which mount /opt/resources:/opt/resources:ro and run as their own UIDs (svc, jonathan-pope) rather than 999 — those users are covered by group:docker today, but 644 makes it unconditional.

Application container structure — the Dockerfile / docker-compose.yml / build.sh / entrypoint.sh pattern, the standard volume mounts, and the test/release split — is documented separately in each repo's CLAUDE.md. This runbook covers only the Postgres container, which runs the stock postgres:16 image and requires no build step. The pg_net network created in Step 6 is persistent once created; app containers attach to it as an external network. - It removes the constraint that only the file's owner can run setfacl — which previously meant that if one developer generated the files, only that developer could complete the permissions steps.

Postgres key permission rules

Postgres enforces strict ownership and permission rules on the private key, and refuses to start if they are violated:

Key owned by Maximum permitted permissions
UID 999 (the database user) 600
root 640

Any group or world access on a key owned by the database user is rejected.

Understanding UID 999

999 is the numeric user ID of the postgres user inside the official postgres:16 image. It is baked into the image; nothing on the host chose it.

The container and the host share one kernel, and the kernel identifies file owners by number only — usernames are a separate lookup performed independently on each side. When Postgres inside the container opens the key file, the kernel asks "is this owned by UID 999?" That is the entire reason the key is chowned to 999.

The displayed name differs between hosts and does not matter:

  • A host running Datadog → ls -l shows dd-agent, because the agent's installer created a system user and got 999 by counting down
  • A host with nothing claiming 999 → ls -l shows the bare number 999

Both are the same owner. The difference is cosmetic and is not evidence that two hosts were built differently.

shell
$getent passwd 999                    # who, if anyone, holds 999 on this host
$docker exec pg_db getent passwd 999  # always 'postgres' — the container's own lookup

The genuine concern: whatever host user holds UID 999 can read the Postgres private key, because to the kernel they are the same user. On a Datadog host that is the monitoring agent; on a host where 999 is unclaimed it is whatever package grabs it next. This works, but it depends on a numeric coincidence rather than an intentional grant. See Cleanup Backlog.

06Run the Container

docker
$docker network create pg_net 2>/dev/null || true
 
# Password via env file — never inline
$umask 077
$cat > /opt/resources/pg.env <<'EOF'
$POSTGRES_PASSWORD=<password>
$EOF
 
$docker run -d \
  --name pg_db \
  --network pg_net \
  --env-file /opt/resources/pg.env \
  -p 5432:5432 \
  -v postgres_data:/var/lib/postgresql/data \
  -v /opt/resources/ssl:/etc/ssl/pg:ro \
  --restart unless-stopped \
  postgres:16 \
  -c ssl=on \
  -c ssl_cert_file=/etc/ssl/pg/pg_ssl.crt \
  -c ssl_key_file=/etc/ssl/pg/pg_ssl.key

Mount the directory, not the individual files. When openssl rewrites a certificate it can produce a new inode; with per-file bind mounts the container keeps seeing the old file until it is recreated. Mounting the directory makes certificate rotation a config reload with zero downtime.

Use an env file for the password. -e POSTGRES_PASSWORD=... inline lands in shell history, ps output, and docker inspect — all readable by anyone in the docker group.

Do not set POSTGRES_HOST_AUTH_METHOD. If it appears anywhere, it is almost certainly someone working around an authentication error, and trust on a public interface is an unauthenticated database.

SSL flags cannot be added to a running container. Applying SSL to an existing container means docker rm -f pg_db and re-running with the same named volume. Confirm the volume is named, not anonymous, before removing anything:

docker
$docker inspect pg_db --format '{{range .Mounts}}{{.Type}} {{.Name}} -> {{.Destination}}{{"\n"}}{{end}}'

A 64-character hash where postgres_data should be means an anonymous volume. It survives the rm but must be reattached by hash — sort that out first.

07Enforce SSL-Only via pg_hba.conf

Back up first

pg_db container
$docker exec pg_db cp /var/lib/postgresql/data/pg_hba.conf \
  /var/lib/postgresql/data/pg_hba.conf.bak

Restore, if needed:

pg_db container
$docker exec pg_db cp /var/lib/postgresql/data/pg_hba.conf.bak \
  /var/lib/postgresql/data/pg_hba.conf
$docker exec pg_db psql -U postgres -c "SELECT pg_reload_conf();"

Apply the change

Replace the catch-all host rule with hostssl. The whitespace-tolerant pattern matters — the official image appends a single-spaced line, but initdb generates column-aligned ones:

pg_db container
$docker exec pg_db sed -i -E \
  's/^host([[:space:]]+all[[:space:]]+all[[:space:]]+all[[:space:]]+)/hostssl\1/' \
  /var/lib/postgresql/data/pg_hba.conf

Confirm it landed — do not skip this

A no-op sed produces no error and leaves a publicly reachable Postgres accepting cleartext connections.

pg_db container
$docker exec pg_db grep -vE '^\s*#|^\s*$' /var/lib/postgresql/data/pg_hba.conf

Expected: exactly one non-local catch-all, reading hostssl. Any remaining host line with a non-loopback address means the substitution failed.

output
# Before
host    all   all   all   scram-sha-256
 
# After
hostssl all   all   all   scram-sha-256

Reload

pg_db container
$docker exec pg_db psql -U postgres -c "SELECT pg_reload_conf();"
$docker exec pg_db psql -U postgres -Atc \
  "SELECT pg_postmaster_start_time(), pg_conf_load_time();"

pg_conf_load_time() must be later than the file's mtime.

pg_hba_file_rules does not tell you what is running. It re-parses the file from disk on every query, so it reflects the file, not the postmaster's live rules. Only Test 2 in the verification suite proves enforcement.

The loopback trust rules are left intact — they apply only to Unix socket or loopback connections from within the container. See the note in Context about what that means for docker group members.

More robust alternative

Keep a version-controlled pg_hba.conf, mount it read-only, and pass -c hba_file=/etc/postgresql/pg_hba.conf. Deterministic and idempotent, rather than a regex against a file you did not write.

08Firewall (NSG)

This is the actual perimeter. -p 5432:5432 binds all interfaces, and Docker's DNAT rules bypass ufw entirely. The Azure NSG is the only effective control.

Resolve the resource group, NSG name, and tenant from the Environments table first — NSG names are identical across environments, so the resource group and tenant are the only things distinguishing them. If a value there is TBD:

azure-cli
$az network nsg list --query "[].{name:name, rg:resourceGroup}" -o table

Back up before changing

shell
$BK=~/nsg-backup-<env>-$(date +%F-%H%M).json
$az network nsg show -g <RG> -n <NSG> > "$BK"
$python3 -c "import json,os;d=json.load(open(os.path.expanduser('$BK')));print(d['name'],len(d['securityRules']),'custom rules')"

The timestamp matters — backups taken on the same day would otherwise overwrite each other, and NSG edits tend to come in clusters.

There is no az network nsg import. The JSON is a reference for reconstructing rules by hand, not a restore mechanism. For a single-rule change the practical rollback is the inverse command (below); the file exists for the case where something unexpected also changed.

Also capture the current rule in a form you can read at a glance, since that is what a rollback actually needs:

azure-cli
$az network nsg rule show -g <RG> --nsg-name <NSG> -n PG_INBOUND \
  --query "{single:sourceAddressPrefix, list:sourceAddressPrefixes, desc:description, pri:priority}" -o json

Create a scoped rule. Do not use '*':

azure-cli
$az network nsg rule create \
  -g <RG> --nsg-name <NSG> -n PG_INBOUND \
  --priority 310 --access Allow --protocol Tcp --direction Inbound \
  --source-address-prefixes <IP1> <IP2> <APP_SERVICE_IPS...> \
  --destination-port-ranges 5432 \
  --description "Postgres SSL - dev workstations + App Service outbound"

Rollback

If the rule did not exist before — delete it:

azure-cli
$az network nsg rule delete -g <RG> --nsg-name <NSG> -n PG_INBOUND

If you changed an existing rule — restore the previous source list and description verbatim from the values captured above:

azure-cli
$az network nsg rule update -g <RG> --nsg-name <NSG> -n PG_INBOUND \
  --source-address-prefixes <PREVIOUS_IPS> \
  --description "<PREVIOUS_DESCRIPTION>"

If the whole NSG needs rebuilding — read the saved JSON and re-create each entry under securityRules. Default rules (priority 65000+) are managed by Azure and are not restored:

shell
$python3 -c "
$import json,os,sys
$d=json.load(open(os.path.expanduser('$BK')))
$for r in d['securityRules']:
$    src=' '.join(r['sourceAddressPrefixes']) or r['sourceAddressPrefix']
$    print(f\"az network nsg rule create -g {d['resourceGroup']} --nsg-name {d['name']} \"
$          f\"-n {r['name']} --priority {r['priority']} --access {r['access']} \"
$          f\"--protocol {r['protocol']} --direction {r['direction']} \"
$          f\"--source-address-prefixes {src} \"
$          f\"--destination-port-ranges {r['destinationPortRange']}\")
$"

That prints the commands rather than running them, so you can review before applying.

CAUTION Rolling back a tightening change re-opens access. Rolling back a widening change can drop live clients — including App Service. Confirm which direction you are undoing before running anything.

Gathering source IPs

curl
# Each developer's egress IP
$curl -s https://ifconfig.me; echo
 
# App Service — possibleOutboundIpAddresses, NOT outboundIpAddresses.
# The latter is only the currently-active subset and changes on scale or restart.
$az webapp show -g <APP_RG> -n <APP_NAME> --query possibleOutboundIpAddresses -o tsv

Space-separated in the CLI, even though Azure returns them comma-separated.

Tightening an existing wide-open rule is the change with real blast radius. NSG changes drop established flows. Before narrowing a Source: * rule, confirm every current client appears in the new list:

pg_db container
$docker exec pg_db psql -U postgres -Atc \
 "SELECT DISTINCT client_addr, usename, application_name
$  FROM pg_stat_activity WHERE client_addr IS NOT NULL;"

Maintaining the allowlist

Adding or removing an IP later uses update, not create. Take a backup first — see Back up before changing:

azure-cli
$az network nsg rule update -g <RG> --nsg-name <NSG> -n PG_INBOUND \
  --source-address-prefixes <IP1> <IP2> <IP3> ... \
  --description "Postgres SSL - <who is covered>"

CAUTION update replaces the entire list — it does not append. Every IP that should keep access must appear in the command, including your own. Omitting yours locks you out of the database mid-session.

Read the current list before editing it, so you are adding to a known set:

azure-cli
$az network nsg rule show -g <RG> --nsg-name <NSG> -n PG_INBOUND \
  --query "{prefixes:sourceAddressPrefixes, single:sourceAddressPrefix, port:destinationPortRange, access:access}" -o json

A single-IP rule reports under sourceAddressPrefix (singular); multiple IPs report under sourceAddressPrefixes (plural). Check both — the field moves as the list grows.

Confirm afterwards from a client machine:

netcat
$nc -zv -w5 <VM_PUBLIC_IP> 5432

Keep the --description current with who is covered. It is the only record of why a given address is on the list, and stale entries otherwise accumulate indefinitely.

Residential and VPN developer IPs rotate, making the allowlist an ongoing support burden. Where a jump box exists in the VNet, SSH tunnelling (ssh -L 5432:localhost:5432 <jumpbox>) is the more durable answer for developer access and allows 5432 to eventually be restricted to App Service alone.

09Verification Tests

Run these from a client machine, not from the VM — the point is to exercise the network path and the certificate exactly as an external client sees them.

Prerequisites

shell
$mkdir -p ~/ssl
$scp <ssh-alias>:/opt/resources/ssl/pg_ssl.crt ~/ssl/pg_ssl_<env>.crt
$openssl x509 -in ~/ssl/pg_ssl_<env>.crt -noout -fingerprint -sha256 -ext subjectAltName
$psql --version    # any version works; see the note under Test 3

Confirm the fingerprint matches the one recorded in Step 4.

Test 1 — Reachability

netcat
$nc -zv -w5 <VM_PUBLIC_IP> 5432
Result Meaning
succeeded PASS NSG allows your IP; proceed
timed out FAIL Filtered — NSG rule missing or your IP changed. No client setting fixes this.
refused FAIL Reachable but nothing listening — container is down

Always run this first. A hanging psql is otherwise misread as an SSL failure.

Test 2 — Unencrypted connection must be REJECTED

psql
$psql "host=<VM_PUBLIC_IP> port=5432 dbname=<db> user=postgres sslmode=disable connect_timeout=5"

Expected:

output
psql: error: FATAL:  no pg_hba.conf entry for host "<your ip>", user "postgres", database "<db>", no encryption

PASS This is the definitive proof that hostssl is enforced. The phrase "no encryption" is the part that matters. It also confirms your source IP as the server sees it.

FAIL If this connects, stop — the sed in Step 7 did not take effect and the database is accepting cleartext connections.

Test 3 — TLS with full certificate verification must SUCCEED

psql
$psql "host=postgres-server hostaddr=<VM_PUBLIC_IP> port=5432 dbname=<db> user=postgres \
sslmode=verify-full sslrootcert=$HOME/ssl/pg_ssl_<env>.crt connect_timeout=5"

PASS A password prompt is a pass. TLS completed and the certificate verified before authentication was attempted. FATAL: password authentication failed is also a pass — that is a credentials issue, not a TLS one.

Use $HOME, not ~. Inside double quotes the shell will not expand a tilde, and libpq does not expand it either.

Why host and hostaddr are split. hostaddr is where the connection goes; host is the name verified against the certificate. This form works on every psql version. Connecting by IP alone fails on psql 15 and older with server certificate for "pg_db" (and 2 other names) does not match host name — libpq only gained iPAddress SAN matching in PostgreSQL 16, so older clients compare against dNSName/CN only. That error is a client limitation, not a bad certificate.

Test 4 — Confirm the negotiated session

psql
$PGPASSWORD='<pw>' psql "host=postgres-server hostaddr=<VM_PUBLIC_IP> port=5432 \
dbname=<db> user=postgres sslmode=verify-full sslrootcert=$HOME/ssl/pg_ssl_<env>.crt" \
-c "SELECT ssl, version, cipher FROM pg_stat_ssl WHERE pid = pg_backend_pid();"

PASS Expected: ssl = t with a TLS version and cipher. Worth pasting into the build record as evidence.

Test 5 — Wrong certificate must be REJECTED

Proves verification is actually happening rather than being silently skipped. Point a different environment's certificate at this host:

psql
$psql "host=postgres-server hostaddr=<VM_PUBLIC_IP> port=5432 dbname=<db> user=postgres \
sslmode=verify-full sslrootcert=$HOME/ssl/pg_ssl_<other-env>.crt connect_timeout=5"

PASS Expected: SSL error: certificate verify failed / self-signed certificate. FAIL If this connects, verification is not being enforced.

Test 6 — Application-layer verification

From the app, not the shell:

javascript
const { rows } = await pool.query(
  'SELECT ssl, version, cipher FROM pg_stat_ssl WHERE pid = pg_backend_pid()'
);
console.log(rows[0]);   // { ssl: true, version: 'TLSv1.3', cipher: '...' }

Summary

# Test Expected
1 TCP reachability PASS succeeded
2 sslmode=disable FAIL rejected — "no encryption"
3 verify-full, correct cert PASS password prompt / auth error
4 pg_stat_ssl PASS ssl = t
5 verify-full, wrong cert FAIL verify failed
6 App reports ssl: true PASS

Tests 2 and 5 prove that only safe, certified connections are allowed. Tests 1, 3, 4 and 6 prove that legitimate clients still work. A build is not complete until all six behave as listed.

Regenerating the Certificate

Required when the certificate expires, the VM IP changes, or a new hostname is added.

openssl
# sudo required because pg_ssl.key is owned by UID 999
$sudo openssl req -new -x509 -days 1095 \
  -key /opt/resources/ssl/pg_ssl.key \
  -out /opt/resources/ssl/pg_ssl.crt \
  -subj "/CN=pg_db" \
  -addext "subjectAltName=DNS:pg_db,DNS:postgres-server,DNS:localhost,IP:<THIS_VM_PUBLIC_IP>,IP:127.0.0.1"
 
# sudo overwrites ownership to root — restore it
$sudo chown $USER:docker /opt/resources/ssl/pg_ssl.crt
$sudo chmod 644 /opt/resources/ssl/pg_ssl.crt
 
# With the directory mount from Step 6, a reload suffices — no downtime
$docker exec pg_db psql -U postgres -c "SELECT pg_reload_conf();"

ssl_cert_file and ssl_key_file are SIGHUP-context settings — Postgres re-reads them on config reload and has since version 10. Hosts still using per-file bind mounts need docker restart pg_db instead, because the mount pins an inode.

Confirm the new certificate is live:

openssl
$openssl s_client -starttls postgres -connect <VM_PUBLIC_IP>:5432 </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -dates -ext subjectAltName -fingerprint -sha256

Rotation has three obligations, not one:

  1. Update Appendix D — Certificates with the new PEM, fingerprint, and expiry, then regenerate and redistribute this document. A stale embedded certificate hands people a copy that fails verification with a confusing error.
  2. Announce it — all developers must re-pull, and all App Service deployments must be updated, or they will fail verification.
  3. Update the SHA-256 in the Environments notes if recorded there.

To pull the new copy from the host:

scp
$scp <ssh-alias>:/opt/resources/ssl/pg_ssl.crt ~/ssl/pg_ssl_<env>.crt

Set a calendar reminder ~60 days before the 1095-day expiry. Nothing in this design warns you.

Auditing an Existing Build

Read-only. Use when inheriting a container someone else set up.

docker
# What the container actually is
$docker inspect pg_db --format '{{json .Config.Cmd}}'
$docker inspect pg_db --format '{{range .Mounts}}{{.Type}} {{.Name}}{{.Source}} -> {{.Destination}} (rw={{.RW}}){{"\n"}}{{end}}'
$docker inspect pg_db --format '{{json .NetworkSettings.Networks}}'
$docker inspect pg_db --format '{{json .NetworkSettings.Ports}}'
$docker inspect pg_db --format '{{range .Config.Env}}{{println .}}{{end}}' | grep -v PASSWORD
 
# What Postgres thinks its config is — the 'source' column distinguishes
# command-line flags from a hand-edited postgresql.conf inside the volume
$docker exec pg_db psql -U postgres -Atc \
 "SELECT name||' = '||setting||'  ['||source||']' FROM pg_settings
$  WHERE name IN ('ssl','ssl_cert_file','ssl_key_file','ssl_ca_file',
$                 'hba_file','listen_addresses','password_encryption');"
 
# The one that matters
$docker exec pg_db grep -vE '^\s*#|^\s*$' /var/lib/postgresql/data/pg_hba.conf
 
# Certificate and key, as the container sees them and on the host
$docker exec pg_db ls -ln /etc/ssl/pg/
$ls -la /opt/resources/ssl/; getfacl -p /opt/resources/ssl/* 2>/dev/null
$openssl x509 -in /opt/resources/ssl/pg_ssl.crt \
  -noout -subject -dates -ext subjectAltName -fingerprint -sha256

Red flags, in priority order:

  1. POSTGRES_HOST_AUTH_METHOD=trust in Env — unauthenticated database
  2. A host (not hostssl) catch-all rule with a non-loopback address
  3. A SAN carrying another environment's IP — certificate was copied, not generated
  4. SSL settings sourced from configuration file rather than command line — someone edited postgresql.conf inside the volume, diverging from this document
  5. Container not on pg_net — DNS:pg_db will not resolve for dockerized apps
  6. Anonymous data volume — makes any container recreate risky

Not problems. A key at 600 owned by root, or 640 owned by root — both are permitted. ls -l showing dd-agent instead of 999. Do not "fix" a healthy container.

Known Divergences on Existing Hosts

Hosts built before this revision differ in ways that are not faults:

Divergence Consequence
Per-file bind mounts instead of the directory mount Certificate rotation requires docker restart pg_db rather than a reload
Certificate at 640 with an ACL granting u:999:r Works; the ACL must be re-applied after every regeneration
-e POSTGRES_PASSWORD inline Password visible in docker inspect and shell history
Docker data-root on the OS disk Verify capacity; relocating later means downtime

Migrating an existing host to the current build is a container recreate — plan it alongside the Cleanup Backlog rather than piecemeal.

02CONNECTION GUIDE

For developers. You do not need VM access to follow this section.

TLS is mandatory on all environments — unencrypted connections are rejected by the server.

Before You Start

You need three things:

  1. The server certificate (pg_ssl_<env>.crt) — copy it from Appendix D. You will never need the private key. If someone sends you a .key file, that is a mistake.
  2. An NSG allowlist entry — port 5432 is closed by default. Send your public IP (see below).
  3. Database credentials — database name, role, and password.
Setting Value
Host (IP) <VM_PUBLIC_IP>
Host (certificate name) postgres-server
Port 5432
Database dev, staging, or prod — matching the host you are connecting to
SSL mode verify-full
Certificate fingerprint (supplied with the cert)

Each environment has its own certificate. They are not interchangeable.

On the VM, the file is always /opt/resources/ssl/pg_ssl.crt — each host is one environment, so no suffix is needed or wanted.

On a developer workstation, you may hold several. Name local copies pg_ssl_staging.crt, pg_ssl_dev.crt to keep them apart, and verify the fingerprint before trusting a copy you did not receive directly.

Dockerized apps on this host need no copy at all — they read the certificate through the standard /opt/resources:/opt/resources:ro mount, with PG_SSL_PATH=/opt/resources/ssl/pg_ssl.crt. Only external clients and App Service deployments need their own copy.

Getting your IP

curl
$curl -s https://ifconfig.me; echo

Send that to the DB owner. On residential or VPN connections this address changes periodically — when connections suddenly time out, re-run this and send the new value. It is the most common cause of "the database is down."

For Azure Web Apps, send the full outbound set instead:

azure-cli
$az webapp show -g <RG> -n <APP_NAME> --query possibleOutboundIpAddresses -o tsv

Use possibleOutboundIpAddresses, not outboundIpAddresses — the latter is only the currently-active subset and changes when the app scales or restarts, which will break your connection at an unpredictable moment.

Certificate placement

The DEV and STAGING certificates are reproduced in Appendix D — Certificates as ready-to-paste blocks. Use those; there is no need to request a copy from anyone.

If you have SSH access and would rather pull it from the host:

shell
$mkdir -p ~/ssl
$scp <ssh-alias>:/opt/resources/ssl/pg_ssl.crt ~/ssl/pg_ssl_<env>.crt
$openssl x509 -in ~/ssl/pg_ssl_<env>.crt -noout -fingerprint -sha256 -ext subjectAltName

The fingerprint must match the one you were given. The SAN should list pg_db, postgres-server, localhost, the VM's public IP, and 127.0.0.1.

WSL users: a Windows IDE cannot read a path inside your WSL filesystem. Copy the certificate to the Windows side as well:

shell
$mkdir -p /mnt/c/Users/<you>/pg-ssl
$cp ~/ssl/pg_ssl_<env>.crt /mnt/c/Users/<you>/pg-ssl/

Then reference C:\Users\<you>\pg-ssl\pg_ssl_<env>.crt in the IDE.

user=postgres sslmode=verify-full sslrootcert=$HOME/ssl/pg_ssl_<env>.crt connect_timeout=5"

Why both host and hostaddr

hostaddr is where the connection goes; host is the name verified against the certificate. Use this form regardless of your psql version — it works on all of them.

Connecting by IP alone works only on psql 16 and newer. Older clients produce server certificate for "pg_db" (and 2 other names) does not match host name "<IP>", because libpq only gained iPAddress SAN matching in PostgreSQL 16. That is a client limitation, not a broken certificate — do not request a new one when you see it.

Express / Node.js

The pg driver passes the ssl object to Node's TLS stack, which does match IP SANs — no hostaddr workaround needed.

javascript
const fs = require('fs');
const { Pool } = require('pg');
 
const pool = new Pool({
  host: process.env.PG_HOST,
  port: process.env.PG_PORT,
  database: process.env.PG_DB,
  user: process.env.PG_USER,
  password: process.env.PG_PW,
  ssl: {
    ca: fs.readFileSync(process.env.PG_SSL_PATH),
    rejectUnauthorized: true,
  },
});
 
module.exports = pool;

Using pg-promise? The config object is identical — pass it to pgp(config).

shell
$PG_HOST=<VM_PUBLIC_IP>       # or pg_db for dockerized apps on pg_net
$PG_PORT=5432
$PG_DB=<db>
$PG_USER=postgres
$PG_PW=<password>
$PG_SSL_PATH=./ssl/pg_ssl_<env>.crt

Things that will bite you

  • ca, not cert. The cert field is for client certificates, which are not used here. Putting the server certificate there silently disables verification. This replaced the Azure Flexi-server BaltimoreCyberTrustRoot.crt.pem setup, where cert was correct — hence the confusion.
  • rejectUnauthorized: true is what enforces verification. Setting it to false gives encryption with no identity check, defeating the point. It defaults to true; just do not override it.
  • require: true does nothing. It is not a tls.connect() option. Harmless, but do not mistake it for a safety net.
  • Ship the certificate with the app. For App Service, it must be part of the deployed artifact and not .gitignore'd out. Reference it by a path relative to the app root, not an absolute local path.

Verify from inside the app

javascript
const { rows } = await pool.query(
  'SELECT ssl, version, cipher FROM pg_stat_ssl WHERE pid = pg_backend_pid()'
);
console.log(rows[0]);   // { ssl: true, version: 'TLSv1.3', cipher: '...' }

ssl: true plus rejectUnauthorized: true not throwing equals full verification.

Troubleshooting

Symptom Cause Fix
Connection timed out / hangs Your IP is not in the NSG allowlist, or it changed Re-run curl ifconfig.me, send it to the DB owner
no pg_hba.conf entry ... no encryption SSL disabled in your client Set sslmode=require or higher / add the ssl block

Separate network problems from TLS problems before debugging anything else:

netcat
$nc -zv -w5 <VM_PUBLIC_IP> 5432

succeeded means the network path is fine and any remaining error is TLS or auth. timed out means an allowlist problem, and no client configuration will fix it.

Rules

  • Never commit the private key. You should never have it — only the .crt is distributed.
  • The certificate is public information. Safe to share internally and to bundle into deployment artifacts. It is not a secret; your password is.
  • If the certificate is regenerated, re-pull it and redeploy. Connections fail with a verification error until you do.

Appendix C — Cleanup Backlog

Deferred deliberately. Several are interdependent — do not address piecemeal.

  • Permission model rework. The key's UID 999 ownership works but depends on a numeric coincidence rather than an intentional grant. Options: a root-owned key with a dedicated group and --group-add; a reserved placeholder system user on 999; a dedicated high UID via --user (requires re-chowning the data volume); relocating certificates out of /opt/resources entirely. Before choosing, inventory what else reads /opt/resources/ssl/pg_ssl.key — backup jobs, configuration management, other containers.
  • Internal CA. Per-host self-signed leaf certificates mean every client must trust every host's certificate individually. One internal root, trusted once, with per-VM server certificates, removes redistribution entirely. This gets more expensive with every VM added.
  • Static IP and a DNS name in the SAN, decoupling certificate lifetime from addressing.
  • Dedicated non-superuser application roles. Everything currently connects as postgres, including applications — which is why this document hardcodes that role. Applications should have their own least-privilege roles; when they do, the Role row in Environments and the connection examples need updating with them.
  • Jump box / SSH tunnel for developer access, replacing rotating residential IPs in the NSG allowlist.
  • Docker data-root placement — confirm it is on the intended persistent disk, not the OS disk and not the ephemeral resource disk.
  • Version-controlled pg_hba.conf mounted read-only, replacing the sed.
  • Certificate expiry monitoring — nothing currently warns before the 1095-day expiry.

Verify what you pasted

Check the copy you just wrote against the fingerprints in the table:

openssl
$openssl x509 -in ~/ssl/pg_ssl_dev.crt -noout -fingerprint -sha256 -dates -ext subjectAltName
$openssl x509 -in ~/ssl/pg_ssl_staging.crt -noout -fingerprint -sha256 -dates -ext subjectAltName

A mismatch means a copy-paste error — a truncated line, or a mail client that wrapped the base64.

A self-signed certificate is its own trust anchor, so a tampered document would hand you a tampered anchor, and the fingerprint printed beside it would have been altered to match. Comparing against the table proves the paste is intact, not that the certificate is genuine. The check that proves that is against the live server:

openssl
$openssl s_client -starttls postgres -connect <VM_PUBLIC_IP>:5432 </dev/null 2>/dev/null \
  | openssl x509 -noout -fingerprint -sha256

Substitute the public IP for the environment whose certificate you are checking — DEV 20.55.72.8, STAGING 20.121.125.115, per Environments. Requires your IP to be on the allowlist. If the result matches your local copy, the copy is the certificate that host is actually presenting.

CAUTION These become wrong the moment a certificate is regenerated. Rotation must include updating this appendix and redistributing the document — see Regenerating the Certificate.

The HTML file is the single distributable — it renders as a readable document, needs no tooling, and carries these instructions in a directive block at the top of the file so they are read before the body.

The seed prompt still matters. This section sits near the end of a long file, and a session opened with "summarise this" will summarise it. Follow Rev Prompts is what redirects it.

Untested. This section is an experiment in making the document self-directing. It has not been validated in practice, so treat anything it produces as a draft to review rather than a command to run unexamined.

On receiving "Follow Rev Prompts"

Use this document as the source of truth and work from the referenced section rather than from memory. Work through the steps below in order — environment first, task second, inputs third.

Every choice must be rendered as clickable options, not as text. If your interface has a tool for presenting selectable choices — an option picker, elicitation widget, multiple-choice or tappable-button component — use it for every question below. The user should be able to answer by clicking, never by typing a number back or retyping an option's wording.

Fall back to a numbered text list only if no such capability exists, and say so when you do.

Use free text only where the answer genuinely cannot be enumerated — an IP address, a person's name, a database role. Never present a free-text prompt where a fixed set of options exists.

The option sets below are the choices to render, not literal output to print.

Step 1 — Ask the environment. Always first, always before anything else.

Question: "Which environment?" Clickable options: DEV · STAGING · PROD

This comes first because every value in every command differs by environment, and because VM names and NSG names are identical across them — nothing can be inferred later. Once answered, look the environment up in Environments and hold its IP, database, NSG, resource group, subscription, tenant, and SSH alias for the rest of the session.

If the user picks PROD, say that PROD has no Postgres host yet — the container has not been replicated there — and ask whether they meant a different environment. Do not proceed with PROD values.

If any value needed later is marked TBD, stop and ask. Do not infer it.

First establish which group they are in — the two lists are different, and most people only ever need the developer one.

Question: "Are you connecting to a database, or administering one?" Clickable options: Connecting (developer) · Administering (infra)

Connect to a Postgres container

The most common request, and the one most likely to come from someone who has never touched the VM. Work these in order. Everything needed is in this document — do not ask the user to request a certificate from anyone.

1. Confirm their IP is on the allowlist

Port 5432 is closed by default, so a missing allowlist entry looks like a hang, and is easily mistaken for a TLS or credentials problem. Check it before anything else.

Have them run:

curl
$curl -s https://ifconfig.me; echo
$nc -zv -w5 <VM_PUBLIC_IP> 5432
  • succeeded — they are on the allowlist. Continue to step 2.
  • timed out — they are not on it, or their IP has changed. Nothing in the client configuration will fix this. Give them the IP from ifconfig.me to send to whoever administers the NSG, or, if the user is that administrator, offer to run task 2 (Add or remove IPs on the allowlist) now.
  • refused — reachable but nothing listening; the container is down. Report it as a server-side problem and stop.

If nc is unavailable, curl -v --connect-timeout 5 telnet://<VM_PUBLIC_IP>:5432 gives the same signal — read only the connect line.

2. Give them the certificate

Take the ready-to-paste block for their environment from Appendix D — Certificates and give it to them directly. Then have them confirm the paste against the fingerprint in that appendix:

openssl
$openssl x509 -in ~/ssl/pg_ssl_<env>.crt -noout -fingerprint -sha256 -ext subjectAltName

A mismatch is a copy-paste error — usually a wrapped base64 line — not a bad certificate.

WSL users: a Windows IDE cannot read a path inside the WSL filesystem. They need a second copy on the Windows side, and must reference the C:\... path in the IDE.

3. Ask how they are connecting

Question: "How are you connecting?" Clickable options: psql · Database IDE · Node.js / Express app · Something else

Then give only that path's setup — not all three.

Choice Work from The thing they will get wrong
psql psql Connecting by IP alone. Give them the host=postgres-server hostaddr=<IP> form, which works on every client version.
Database IDE Database IDEs Ask which IDE and give that one's panel. In Beekeeper the certificate fields only appear after SSL is toggled on; leave "trust server certificate" unchecked.
Node.js / Express app Express / Node.js ca: not cert:. cert is for client certificates and silently disables verification. Also ensure the certificate ships with the App Service artifact and is not gitignored.
Something else Free text Establish whether the client verifies IP SANs. If unsure, have them use postgres-server as the host.

They will also need the database name and the password. Both the database and the role (postgres) are in Environments. The password is not in this document and must never be added to it — say so and point them at whoever owns credentials.

4. Confirm it worked

psql
$psql "host=postgres-server hostaddr=<VM_PUBLIC_IP> port=5432 dbname=<db> user=postgres \
sslmode=verify-full sslrootcert=$HOME/ssl/pg_ssl_<env>.crt connect_timeout=5"

A password prompt means TLS completed and the certificate verified — that is success before credentials are even considered. password authentication failed is also a TLS success; send them to whoever owns credentials.

For an app, have them run this once connected:

javascript
const { rows } = await pool.query(
  'SELECT ssl, version, cipher FROM pg_stat_ssl WHERE pid = pg_backend_pid()'
);
console.log(rows[0]);   // { ssl: true, ... }

If anything fails, go to Troubleshooting and match the exact error text rather than guessing.

Before running anything destructive

Establish whether the change is additive or subtractive, and say which out loud before generating the command. Adding an allowlist entry is safe. Narrowing one drops live connections — including App Service, which reaches Postgres over the public IP. The same asymmetry applies to rollbacks: undoing a tightening re-opens access, undoing a widening can drop clients.

Standing constraints

  • Before any Azure command, confirm the shell is authenticated to the intended tenant — az account show — because the same command hits a different environment depending on the active session. Do not assume, and do not require a particular wrapper; plain az is correct.
  • Never substitute '*' for an NSG source prefix.
  • Never generate a command that omits the user's own IP from an allowlist they are connected through.
  • Treat sslmode=disable succeeding, or a wrong certificate being accepted, as alarms rather than passing results.
  • If a value is unknown, ask. A plausible-looking IP, resource group, or tenant ID is worse than a question.
  • Prefer read-only commands until the user has confirmed the state they expect.
