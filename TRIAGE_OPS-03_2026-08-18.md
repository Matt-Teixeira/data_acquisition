## A. FIX LIST — real defects, stable, code/data-addressable

### A1. ⭐ NEW: a stored credential has never decrypted — `Invalid authentication tag length: 0`
Every run of all six data-grab families (`get_ge_ct/cv/mri`, `get_philips_ct/mri`, +1) throws
exactly one `TypeError: Invalid authentication tag length: 0` at `Decipheriv.setAuthTag` —
288 runs/day, every day, constant. Meaning: at least one encrypted credential record in the
database is malformed (empty auth tag) and has NEVER been decryptable — whatever system(s) it
serves has been silently skipped on every acquisition cycle. The catch logs `note: null`
(no record context — a job-layer gap), so next step is tracing which record:
read the decrypt loop in `util/encrypt/` + the credentials table, find row(s) with zero-length
auth tag, then re-encrypt via the documented credential process. **Owner: Claude (trace) → Matt
(re-encrypt).**

> **Scope update 2026-08-18 (from the new tracking data):** this is **not one malformed record**.
> The now-contextual logs show **79 of 148 HHM systems failing across all 20 credential groups in
> use** — i.e. *every* credential group in the staging database fails to decrypt, affecting GE
> CT/CV/MRI and Philips CT/MRI alike. A whole-fleet symptom points at the key/format rather than
> the rows: most likely the staging `APP_SECRET` does not match the key these values were
> encrypted with, or the migration that populated staging altered the stored ciphertext format
> (the auth tag arrives zero-length). Trace deferred by owner decision; visibility is in place.
>
> **Correction 2026-08-18 14:00 — an earlier note in this document claimed "credentialed HHM
> acquisition has never functioned on this staging server." That was wrong.** Checked against
> `stats.acquisition_history` (independent of the tracking tables, current to 13:50 today):
> the HHM pipeline *is* succeeding, but for only **12 systems** since 2026-07-08, versus **154 on
> the mmb pipeline**. So the failure is severe and broad, not total. Also softening the impact:
> **20 of the 79 credential-failing systems still deliver data through the mmb pipeline**
> (29,862 acquisitions since July 8) — they are missing their HHM log data specifically, not dark.
> The remaining 59 have no successful acquisition on either pipeline.
>
> **Update 2026-08-18 12:31 (commit `eb682a7`), corrected 13:20 (commit `7f8a57d`):** the failure
> is now part of the error profile: `execHhmSystem` catches argsBuilder/decrypt throws, logs them
> WITH `system_id`/`credentials_group` context, and pushes a `conn_err` entry with
> `error_category='credential_decrypt'` into the Redis online queue, so the standard
> `offline_alert` job (:22/:52) upserts it into **`alert.offline_hhm_conn`** like any other
> connection failure. Side benefit: one bad credential no longer rejects the family's whole
> Promise.all. The tracking table will now name the affected system(s) on its own.

## B. SITE / OPS LIST — environmental; needs inventory reconciliation, not code

### B0. ⭐ THE JULY 7 EVENT — 23 systems went dark simultaneously (added 2026-08-18)

Deeper cut of B1: the 103 rsync-failing systems are **not** one population. They split into
**63 that succeeded within 48 h** (intermittent VPN flakiness — no action), **~84 long-tail
stalled systems** dating back to 2024 (genuine retirement list), and **23 that all last
succeeded on exactly 2026-07-07**. Every other last-success date cluster in the entire table is
≤7 systems, so this is one event, not 23 site problems.

Facts established (read-only):
- **All 23 are MRI**, spanning **GE, Philips and Siemens** and **21 distinct customer sites**.
- **No code cause:** zero commits in any app repo between 2026-07-04 and 07-10.
- **Tunnels are up:** none of the 23 appear in `getTunnelsByIP` "NO TUNNEL FOUND" warnings —
  the VPN path exists; the far-end transfer fails (`rsync I/O timeout`, `connection closed by
  peer`, one `no route to host`). Consistent with equipment powered down/replaced, site-side
  firewall/credential change, or access withdrawn — **not** a VPN-routing failure here.
- **Cost of leaving them configured:** `lifetime_total` is a *reset-intervention* counter
  (`system_reset_totalizer.js`), not an acquisition count. These systems average **1,824 resets
  each** vs **151 for working systems** — ~42,000 futile retry/reset cycles in six weeks, and
  they are the single largest contributor to the nightly error volume.
- **22 of 23 still have `show_on_website = true`** — so whatever happened, the inventory flags
  were never updated.

**RESOLVED PARTLY — owner supplied production flags 2026-08-18.** The contract hypothesis
explains only a minority, and the comparison exposed a second, structural problem:

| Group | Count | Meaning |
|---|---|---|
| Retired in prod, **still active in staging** | **6** | `SME14950, SME16411, SME16421, SME16422, SME16432, SME16433` — prod has `show_on_website=false` + `process_mag=false` (5 also `process_log=false`); staging still says `true` on all three, so this server keeps polling them |
| Retired in **both** | 1 | `SME15166` — correctly stopped |
| **Active in both prod and staging** | **14** | Production still expects data. Dark since 2026-07-07 → **a genuine six-week outage needing tickets** |
| Not in the prod list at all | 2 | `SME02524, SME11247` — fully active in staging; confirm whether deleted from prod inventory |

**Two actions fall out:**
1. **Sync the 6 retired systems' flags into staging** (`show_on_website`, `process_mag`,
   `process_log` → false). They stop being polled, which removes a chunk of the ~42,000 futile
   reset cycles. → see B0a below, which is the bigger version of this problem.
2. **Escalate the 14 (+2 unconfirmed) as a real outage.** Production considers them live; they
   have delivered nothing since 2026-07-07. Tunnels are up, so this is site/equipment-side.

### B0a. ⭐ STRUCTURAL: staging's `public.systems` inventory drifts from production

The comparison above is the symptom; the disease is that **nothing syncs system inventory from
the production (Azure) database into this staging database.** `public.systems` was populated by a
point-in-time `pg_manage_v2` migration and has diverged since. Consequences: this server polls
equipment production has retired (wasted work, inflated error counts), and **inventory flags in
staging cannot be trusted for operational decisions** — including decisions made from this very
triage document. Any "dead or alive" question must be answered against prod.

**Action:** decide the intended sync mechanism (periodic re-migration of `public.systems` +
`config.acquisition`, or an explicit reconciliation job), and add an inventory-drift check to the
acceptance gate. This belongs in doc 2.1 as a named data-ownership decision, not an ad hoc fix.
