**Result: P1: 0, P2: 3, P3: 0 new findings.** The original F1–F4 and destructive R1 scenarios are fixed. **New findings, most severe first**

**N1 — P2: a failed or timed-out listing can replace the previous listing with partial data.** `read/sh/Philips/phil_ct_data_grab_1.sh:128–131`.

The return status of `timeout … lftp` is ignored. Publication depends only on whether its staging file is nonempty. A listing that writes some entries and then fails, including one interrupted at its deadline, therefore replaces a complete previous `Data_Logger.ls`. Its new mtime also makes it look fresh for the next day. This can hide archived databases—the evidence this listing was added to collect—while reporting successful acquisition.

Reproduced: the listing stub wrote an incomplete listing, printed a failure and exited 1. The collector exited 0 with empty stderr and installed the incomplete listing over the old file. The Jest failure stub exits before creating any listing, so that test misses this case.

Suggested fix: require successful completion of the timeout/lftp command as well as a nonempty staging file before installing it. Retain the previous listing on any nonzero command status. Keep the optional session's errors isolated from the acquisition runner, including errors from installing the listing.

**N2 — P2: the optional listing's 120-second limit does not enforce termination.** `read/sh/Philips/phil_ct_data_grab_1.sh:128`, together with the inherited lock at lines 36–40.

GNU `timeout 120` sends TERM at the deadline; without `--kill-after`, it can continue waiting indefinitely for a command that catches or ignores TERM. The collector waits for this optional session after publishing the required outputs, and the session retains fd 9. In that state the runner never receives this invocation's success and subsequent grabs exit 75 indefinitely. The handoff's statement that the listing cannot change the acquisition result overlooks whether the script returns at all.

Reproduced with a listing stub that ignores TERM and a wrapper scaling only the real GNU timeout duration from 120 seconds to 0.15 seconds. After the scaled deadline the collector was still running and a second grab returned 75. Releasing the stub allowed cleanup and termination. This establishes the conditional failure; it does not establish that installed lftp normally ignores TERM.

Suggested fix: use a finite hard-kill grace, for example `timeout -k 10s 120s lftp …`, with process-group signaling so transport children are covered too. Check its result before installing the listing (N1). Keep private staging and writer lock inheritance. Do not rely solely on a shell EXIT trap for descendant termination.

**N3 — P2: unsuccessful listings bypass the stated daily connection limit.** `read/sh/Philips/phil_ct_data_grab_1.sh:127`.

The throttle measures the age of the last published listing, not the last attempt. When there is no listing, or it is stale, a failed attempt leaves the condition true. Every 15-minute acquisition then opens another listing session: up to 96 attempts per day even without resets, rather than approximately one. A server that permits fetching a known file but denies directory enumeration is a realistic persistent case. If each session reaches its timeout, this adds roughly two minutes of locked work to every grab before accounting for N2.

Reproduced three immediate successful main acquisitions with a stale listing and a failing listing stub: all three launched a listing session, all returned 0, and the old listing remained stale.

Suggested fix: track attempt time separately from the last successful listing. Apply the intended daily throttle, or an explicitly bounded retry/backoff policy, after failure while retaining the last good evidence. A shrink can still force an attempt independently. If retrying every grab is intentional, the claimed daily bound must be withdrawn; it is not what the current policy guarantees.

**Disposition of the first review**

- **F1 — fixed for the reported race.** Private staging prevents pathname reuse between acquisitions, and lftp retains the lock while it can write. The new orphan test checks rejection of a second grab while the writer survives and successful publication of the next grab's own database afterward. I additionally verified the installed real lftp, strictly over local `file://` with startup configuration disabled: fd 9 remained open and contention returned 75 after its parent shell was killed. Lock liveness and stale-cleanup assumptions are addressed below.
- **F2 — fixed.** Status 75 is distinguished from other flock errors, and both take a nonzero collector exit. The actual runner tests demonstrate that a skip no longer queues a successful acquisition. Operational flock failure returns 1. Logging ordinary overlap as an error is noisy but honest; it does not reopen the original false-success bug.
- **F3 — fixed for the stated deployment access policy.** Required published files are explicitly chmodded to 0644 before publication, and the umask test exercises that result. This establishes mode independently of ambient umask. It does not preserve arbitrary existing ownership/group/ACL arrangements; the handoff explicitly says those are unnecessary here. I did not inspect production to verify that deployment premise.
- **F4 — fixed.** Required-file publication reports the failed file and the files already installed. `mv -fT` also correctly fails when a target is a directory. The test checks the actual mixed on-disk state. Whole-set rollback remains intentionally absent.
- **R1 — fixed for the destructive transformation failures reported previously.** Each data transformation and header write now has a checked status, so a failed sort cannot silently publish header-only legacy input. The tests cover the first sort and a failing `mdb-tables` that emits plausible stdout. One narrower status-check gap remains at lines 77–78: table-name extraction still uses unchecked sed pipelines, relying on nonempty names and subsequent exports. For example, a sed that prints the requested complete names and then exits nonzero is not treated as a failure. That example does not itself corrupt the exported data, so it is not another counted correctness finding, but “every step checked” is too broad.
- **Q4 — the original connectivity-classification bug is fixed; the broader isolation claim needs qualification.** Listing lftp stdout/stderr is discarded in a separate session. Its timeout diagnostic no longer enters the main-session connection regexes. However, the session can block completion (N2), and the listing's `chmod … && mv …` at line 131 is outside that redirection. I reproduced a directory at the final listing path: the required exports published and the collector exited 0, but an mv diagnostic escaped on stderr. That ordinary diagnostic did not demonstrate a false connection classification. It does contradict the unconditional “stderr empty” guarantee and should be covered when making the whole optional operation best effort.

**Answers to the six “Please look hard at” items**

1. **Lock lifetime: safer for data, still needs a bounded lifetime. Recommendation: add a configurable 600-second main-download deadline with a 15-second hard-kill grace.** Start with `timeout -k 15s 600s lftp …`, retaining process-group signaling rather than `--foreground`. The timer must cover connection setup, retries and transfer together. A roughly 10 MiB transfer in 600 seconds requires about 17 KiB/s before setup/retry overhead; this is an initial operational choice, not a measured guarantee for these VPNs. Measure successful durations and tune the bound while leaving room inside the 15-minute schedule for exports and the optional 120-second listing. If required transfer times exceed that budget, adjust the schedule or acquisition strategy explicitly.

   `net:timeout 20` and a retry count do not impose a total wall-clock cap on a transfer that continues making slow progress. All commands retaining fd 9 can prolong the lock, including transports that are no longer writing local staging. A surviving descendant after its parent exits also needs supervision; a timeout of only a leader that has already exited cannot automatically clean up that descendant. Keep the lock in actual staging writers, and verify transport cleanup/descriptor handling rather than asserting every descendant behaves identically. I confirmed real lftp's descriptor retention, not real SSH's. Make the listing deadline a hard bound too (N2).

   Under the current main-download failure handler, a timeout command's nonzero status would still produce the existing synthetic timeout marker and exit 0, routing it through the runner's established connection-failure handling. Test this deliberately; do not accidentally change it to acquisition success or leave a descendant holding the lock. No scanner timing was measured in this review.

2. **Stale cleanup: sound under the collector's controlled assumptions, not an unconditional theorem about live processes.** With the same stable `.grab.lock` inode, cooperative current collectors, and every local staging writer retaining the locked open-file description, acquiring the lock means those earlier writers have released it. Private directories then make cleanup of previous staging safe. Acquiring a flock does not prove that every earlier descendant has exited: programs can close inherited descriptors, and external removal/recreation of the lock file would split the lock domain. Neither is done by this collector. The installed local lftp check and the orphan test support the relevant writer assumption. Do not broaden this reasoning to unrelated tools, old versions that closed the descriptor, or arbitrary external manipulation of the lock file. Removing stale directories under the lock is otherwise reasonable.

3. **Exit 75: acceptable now; a dedicated runner outcome is the better eventual interface.** It removes the false acquisition record without a runner change. It also creates an ERROR event for ordinary contention and returns null, rather than distinguishing a normal skip from an acquisition fault. At this scope that is a defensible trade. If overlap becomes routine, explicitly handle 75 as a skip in the runner, leave acquisition queues unchanged, and log it at an appropriate non-error level. Do not restore exit 0 without corresponding runner handling. Long runs should be bounded and observable rather than hidden by that outcome.

4. **Listing policy: reasonable heuristic, with failure and reset limitations.** A smaller MDB is useful evidence of a reset, but not a complete reset detector: a rebuilt file can retain its allocation size or grow beyond the previous size before the next grab. A shrink can also be compaction rather than a reset. This should remain described as a heuristic. If a shrink-triggered listing fails while the existing listing is fresh, the next equal-sized grab no longer triggers that reset retry; it waits for the normal age condition. A pending reset-listing flag or bounded retry policy would improve evidence collection.

   The installed `find -mmin +1440` selects a file older than 1440 minutes; local boundary probes just below and above that age behaved as intended. The next scheduled grab adds normal scheduling delay. Separate-session overhead includes another connection/authentication and potentially multiple directory requests. Successful daily listings bound ordinary overhead, but failed attempts do not currently have that daily bound (N3). Nonzero partial results must not replace the last good listing (N1).

5. **Partial publish: agree with the narrow existing-parser reasoning.** The two legacy files have separate reader cursors, so a mixed pair does not itself require a cross-file rollback. Individual renames still prevent a reader from seeing half of a file. The revised error message correctly exposes partial state, and cleanup intentionally discards the uninstalled staging files. This does not promise a consistent database/CSV generation for future consumers, or fix the pre-existing races between path-based size measurement, reading and cursor advancement.

6. **Peak disk: improved, but the handoff's expression is not a safe general sizing formula.** Immediately before cleanup at line 89, staging can contain both `events.raw` and `ealinfo.raw`, plus the Events tr output `ev.1` and the growing awk output `ev.2`. During sort, input and output coexist, and GNU sort may additionally use temporary scratch space outside staging. CSV cleanup now sensibly limits the number of simultaneous raw CSV exports.

   A useful explicit early-stage accounting is old published set + new database + raw Events + raw EALInfo + tr Events + awk Events, plus small metadata/header files. Other phases have their own input/output overlap. A budget based only on one largest raw file plus the final staged exports can underestimate the peak depending on filtering/BLOB sizes; measure the high-water mark and sort scratch requirements on representative data. Removing `events.raw` immediately after successful tr, and generating the EALInfo raw export only when its processing starts, would reduce the early peak further. These are sizing improvements, not additional counted correctness bugs: the newly checked processing steps now protect published input on ordinary pre-publication space failures.

**Remaining test gaps**

- Listing output written before nonzero exit or timeout (N1); verify the previous file and its mtime remain unchanged. The current failure stub exits before writing anything.
- A listing that ignores TERM, transport descendants that outlive their leader, and hard-deadline cleanup (N2). Add main-download deadline tests after introducing that recommendation, including the runner outcome and subsequent lock acquisition.
- Repeated failures with an absent/stale listing, and failure after a shrink while a good listing is fresh (N3 and item 4). Test the chosen attempt/backoff policy separately from publication time.
- Listing chmod/move failure, including the final listing path being a directory, and preservation/isolation of the resulting diagnostics. Required-output publication failures are tested; optional-listing publication is not.
- Failure of the later EALInfo sort, each other transformation, CSV NUL-removal tr, chmod, mktemp and header redirections. Existing sort injection always fails the first Events sort. Checked code is present, but removing several individual guards could still pass the suite. The table-name sed pipelines also retain the status gap noted under R1.
- Required-file publish failure at the first and later CSV moves. The current directory-target test exercises only Events.output. Check reported installed-file lists and preservation of uninstalled targets.
- Normal-exit cleanup and orphan lock lifetime are tested together with private staging, but staging privacy itself is weakly distinguished: changing mktemp to one fixed directory while retaining lock inheritance can preserve the tested contention behavior. If privacy is an explicit independent guarantee, assert distinct staging paths across invocations.
- The orphan and lock-holder tests use fixed sleeps for readiness. Use an explicit ready/release handshake to avoid scheduler-dependent failures on a loaded runner. A long-lived non-writing descendant is not exercised by the current sleeping writer stub.
- The standalone “stubs shadow” test detects a wrong PATH but does not stop Jest from running subsequent direct tests after an assertion failure. The runner wrapper correctly refuses execution. Apply an equivalent refusal to direct script invocations if the safety guarantee must hold even when stub setup regresses. This review additionally used an outer deny stub, so an internal setup failure could not fall through to real lftp.
- CSV literal backslashes, doubled quotes, CRLF, tabs and non-ASCII remain untested here as acknowledged. It is reasonable for decoding tests to live with PCT-1b; this suite's canned exporter fixtures plus argv assertions validate invocation/control flow, not the installed exporter's dialect implementation. Separate real-data equivalence evidence was not rerun.
