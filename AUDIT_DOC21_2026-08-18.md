# Independent Audit — `docs/docker_server_full_setup_2.1.md`

**Date:** 2026-08-18 · **Auditor:** independent read-only pass (Claude), not involved in writing doc 2.1
**Reference server:** acq-vm-0 (staging), live state enumerated server → doc per the audit brief
**Method:** full read of the 1,303-line doc; live enumeration of docker state, crontabs, `/opt/*` trees,
ACLs, sysctl/systemd, per-repo branches/files/compose configs; read-only psql/redis checks; prior audit
material (`AUDIT_RECONCILIATION_FINDINGS_2026-08-14.md`, `PLAN_OF_ATTACK_2026-08.md`,
`TRIAGE_OPS-03_2026-08-18.md`) opened only **after** the findings list was drafted.

---

## 1. Verdict

**A competent operator following this document top-to-bottom on a blank VM would first break at
STEP 2**: the database step runs compose from `/opt/apps/pg_manage_v2/infra/pg_db`, but nothing
before STEP 5 clones `pg_manage_v2` — and before even that, every `git clone git@github.com:...`
requires GitHub SSH credentials the doc never provisions. Both are recoverable by a competent
operator (clone earlier, set up a key), so the build would likely limp forward — until **STEP 4
(Redis seeding), which cannot be executed as written**: the referenced `redis_migrate.sh` does not
exist anywhere on the designated source server. A **dev**-flavor build additionally breaks at STEP 5
because `pg_manage_v2` has no `DEV` branch despite the identity table promising one. The finished
server would run the job fleet correctly (the core recipe — database, Redis, apps, schedules,
backups — is accurate and verified below), but it would **not match acq-vm-0**: no Datadog agent
(which the acceptance test itself depends on), no odd-jobs (partition maintenance would silently be
missing until the watchdog's first firing), and several doc claims (the `edu` schema, `.env.example`
placeholders, "zero compose warnings") are false against today's live state. Verdict: **close to
proven, not yet proven** — the acceptance rebuild (plan item 13) would surface every blocker below
in its first hour, which is exactly what that item is for.

## 2. Findings

### Blocker-on-new-build

**A21-01 — STEP 2 uses a repo that is not cloned until STEP 5**
- Doc: STEP 2 (line 249) `cd /opt/apps/pg_manage_v2/infra/pg_db && docker compose up -d`; the clone
  of `pg_manage_v2` appears only in STEP 5 (line 414). STEP 2 also depends on the TLS material and
  says "Generate the TLS material FIRST (see DATABASE SSL SETUP below)" — a called-out forward
  reference, but the missing clone is not called out at all.
- Evidence: doc order 2 → 5; on a blank VM `/opt/apps/pg_manage_v2` does not exist at STEP 2.
- Fix (describe only): move the `pg_manage_v2` clone (and its `git switch <branch>`) into STEP 2, or
  add a "clone the infra repos first" step before STEP 2 alongside the TLS forward-reference.

**A21-02 — STEP 4's seeding script does not exist**
- Doc: line 385 `./redis_dumps/redis_migrate.sh  # ships latest RDB to ~/redis_dumps/ on the target`.
- Evidence: `grep -rn redis_migrate /opt/apps/` matches only doc 2.0/2.1 themselves;
  `~/redis_dumps/` contains only `redis-PROD-dump-*.rdb` files (newest 2026-07-07), no `*.sh`. The
  doc names acq-vm-0 as the reference/source for the next build, and the script is not on it, in any
  repo, or given a home (the `./` path has no stated cwd/repo).
- Fix: commit the script to `redis-admin/scripts/` (the declared home for Redis scripts) or replace
  the step with explicit `docker cp`/`scp` commands; state which machine and directory the command
  runs from.

**A21-03 — No step provisions GitHub SSH access**
- Doc: every repo acquisition is `git clone git@github.com:Matt-Teixeira/...` (first at line 325);
  the GIT CONFIG section sets only `user.name`/`user.email`. Nothing creates `~/.ssh`, a deploy
  key/PAT, or GitHub's host key.
- Evidence: `grep -in 'ssh-keygen\|deploy key\|~/.ssh' docs/docker_server_full_setup_2.1.md` → no hits.
- Fix: add a step (before the first clone) covering key generation/enrollment (or secret-store
  restore) and `known_hosts` seeding for github.com.

**A21-04 — Dev build: `pg_manage_v2` has no `DEV` branch**
- Doc: identity table (line 20) says admin repos use `DEV` on a dev server; branch map repeats it.
- Evidence: `git -C /opt/apps/pg_manage_v2 branch -r` → `origin/PROD origin/STAGING` only.
  (`redis-admin` does have `origin/DEV`; all eight app repos have `origin/DEV_docker`.)
- Fix: create the branch, or note in the identity table that pg_manage_v2 currently has no DEV
  branch and which branch a dev build should use.

### Drift (doc vs live server / repo)

**A21-05 — The `edu` schema claim is false (and was already flagged pre-2.1 as DB-08)**
- Doc: STEP 5.4 note (line 456) — "schema `edu` has no tables".
- Evidence: `SELECT ... information_schema.tables WHERE table_schema='edu'` → **20 tables**
  (`v1`/`v2`/`v3` + monthly partitions 2026_03…2026_09 + units tables), with real data
  (`edu.v2_2026_07` reltuples ≈ 42,026; `edu.v3` ≈ 6,635). The other half of the claim holds:
  `mag.ge_mm` is absent (only `ge_mm3`/`ge_mm4`).
- Reconciliation: the 2026-08-14 audit flagged exactly this staleness as **DB-08** against doc 2.0;
  doc 2.1 (written 2026-08-18) carried the stale sentence forward anyway.
- Fix: update the known-gaps note; per DB-08, consider a schema-contract check for code expecting
  `mag.ge_mm`.

**A21-06 — REL-07 placeholder claim is violated by tracked `.env.example` files**
- Doc: CONVENTIONS (line 64) — examples "carry placeholders, not staging's real numbers"; acceptance
  test — "Committed `.env.example` files contain placeholders only — no real uid/gid/tag values."
- Evidence (`grep -nE '=(105|987|1006|...)' /opt/apps/*/.env.example`):
  - `acquisition-v2/.env.example:47-50` — **`DOCKER_GID=987`, `UID_0=105`, `UID_2=1006` as live
    assignments** (staging's real ids).
  - `monday/.env.example:10` — `PGDATABASE=dev`: the exact value doc 2.1 line 1011 calls "the
    pre-August standing failure (REL-02)", waiting to poison the next `cp .env.example .env`.
  - `PGDATABASE=staging` hardcoded in the examples of data_acquisition, hhm_rpp_ge/philips/siemens,
    acumatica_sync, part-source-pipeline, reports, ops-dashboard; `RUN_ENV=staging`/`LOGGER=staging`
    in incident-engine's — and the incident-engine and ops-dashboard steps instruct
    `cp .env.example .env`.
- Reconciliation: plan tracker item 12 says "REL-07 fixed in all 8 repos" — acquisition-v2 and
  monday's `PGDATABASE` evidently weren't in the eight.
- Fix: replace the acquisition-v2 ids and monday's `PGDATABASE=dev` with placeholders; either make
  the remaining `PGDATABASE=staging` values `<DB_NAME>`-style placeholders or have the doc state
  that examples ship the staging identity and must be re-pointed per the identity table.

**A21-07 — Acceptance criterion "zero compose warnings" fails on the reference server itself**
- Doc: acceptance test — "every `docker compose config` validates with **zero warnings**".
- Evidence: `docker compose config --quiet` is clean in 12 of 13 compose projects, but
  **acumatica_sync emits 12 warnings** (`The "expand"/"format" variable is not set`) — an inherent
  consequence of its deliberate no-`env_file` dotenv design (REL-02) that the doc itself documents
  at line 972.
- Fix: scope the acceptance checkbox ("zero warnings except acumatica_sync's known `$expand/$format`
  interpolation warnings") or silence the warnings (e.g. `$$` escapes in `.env` are not an option —
  the app reads it raw — so an exemption note is the honest fix).

**A21-08 — `docs/schedules.md` violates its own manifest contract**
- Doc: STEP 9 — schedules.md is "the manifest: a schedule that is not in it does not exist, and it
  must be kept in sync with `crontab -l`".
- Evidence: the file's "Live crontab (verbatim, 2026-07-27)" block predates the 2026-08-17/18
  installs. Present in live `crontab -l` but absent from the verbatim block: the `05,35`
  `delete_old_db_files` retention line, `15 2 * * * backup.sh`, `30 3 * * * prune-run-logs.sh`,
  `0 9 3,25 * * check-partition-horizon.sh`. (The prose stagger table *does* list them — the two
  halves of the same file disagree.) The svc-crontab odd-jobs schedule (14:00 UTC 1st) appears in
  doc 2.1's STEP 9 table but nowhere in schedules.md.
- Fix: refresh the verbatim block to the current crontab (snapshots exist at
  `/opt/resources/backups/crontab-20260818-1745.txt`) and add a svc-crontab section or pointer.

**A21-09 — Security baseline omits the accepted part-source-pipeline history credential**
- Accepted decision (2026-08-18, not re-litigated here): the SFTP credential in psp's git history
  stays; vendor cannot rotate.
- Doc: SECURITY BASELINE — "**No secrets in any repo** — rotated and scrubbed 2026-08-17; a repo
  scan for credentials must come back empty"; acceptance test — "a secret scan over every repo finds
  nothing". Neither mentions the accepted exception (`grep -in sftp` in the doc finds only the SSH
  bundle and follow-up 4i).
- Consequence: a history-aware scan on the acceptance rebuild **will** find the credential and the
  operator has no way to know it's accepted; the baseline as written is unsatisfiable.
- Fix: record the exception in SECURITY BASELINE and scope the acceptance checkbox (worktree scan
  clean; psp history hit = accepted risk, dated).

**A21-10 — Fleet `RUN_ENV` claim: acumatica_sync is also unset, not just psp**
- Doc: CONVENTIONS run-logs note (line 95) grants a nit exception for psp only; "What changed" says
  "`RUN_ENV=staging` fleet-wide".
- Evidence: `acumatica_sync/.env` has `RUN_ENV=` (empty). Same else-branch outcome (central
  routing), same fix instruction; the doc just doesn't know about it. ops-dashboard also leaves it
  unset (harmless for a service that isn't a job app).
- Fix: extend the nit note or set the values.

### Gap (host state the doc never creates)

**A21-11 — Datadog is load-bearing for the doc but is never installed**
- Evidence: `dd-agent` (uid 999) has been running since Jun 03 (`/opt/datadog-agent/bin/agent`,
  plus security-agent and trace-agent). The doc references dd-agent six times **as a threat model**
  (SEC-06 layout, chown 999 rationale) and the acceptance test requires
  `sudo -u dd-agent cat .../pg_ssl.key → Permission denied`.
- On a blank VM: no Datadog → `sudo -u dd-agent` fails with "unknown user" (acceptance step
  unrunnable, not "denied"); uid 999 may be grabbed by a different package, changing the collision
  the SEC-06 layout is designed around; and the rebuilt server silently loses host monitoring —
  a "match this one" failure the doc cannot see because the agent predates it.
- Fix: add a monitoring step (install method, key from secret store) or explicitly declare Datadog
  out of scope and rewrite the acceptance line to condition on the agent's presence.

**A21-12 — odd-jobs has no provisioning path**
- Doc: STEP 7 — odd-jobs "must exist and run on any server that hosts the database"; PARTITION
  MAINTENANCE — owner is Jonathan, schedule lives in the svc crontab. Correct as ownership
  documentation, but **no step gets it onto a new server**: no deploy hand-off, no "coordinate with
  Jonathan before go-live" checklist item, no acceptance checkbox that the svc crontab entry exists.
- Evidence: live `/opt/apps/odd-jobs/` is a non-git deployment (`.env`, vendored `node_modules`,
  `jobs/pg-part-arch.js`, images `odd-jobs:svc`/`odd-jobs:jonathan-pope`) — none of which the doc
  reproduces. A new DB server runs without partition maintenance until the watchdog's first firing
  (up to the 3rd of the following month).
- Fix: add a "before go-live" item: Jonathan deploys odd-jobs + svc crontab entry; verify via
  `sudo crontab -l -u svc` and the watchdog query.

**A21-13 — Host `psql` is used but never installed**
- Doc: STEP 5.4 (`psql -h localhost ...`) and the SSL verification tests (`psql "host=<VM_IP> ..."`)
  run `psql` on the host. The doc installs Docker only; a blank Debian VM has no psql
  (`postgresql-client` is not part of any doc step). Live box has it (`/usr/bin/psql`) — accumulated
  state.
- Fix: add `sudo apt install -y postgresql-client` (or route those checks through
  `docker exec pg_db`/`docker run --network pg_net`, matching the container-only philosophy).

**A21-14 — "hostssl-only" is only true for the catch-all; loopback trust remains, and the doc's own
commands depend on it**
- Doc: SECURITY BASELINE "Postgres: hostssl-only"; STEP 2 verification implies the pg_hba edit
  yields SSL-only access.
- Evidence: `pg_hba_file_rules` → line 128 `hostssl all all all scram-sha-256` (the edited
  catch-all), but lines 117–126 are stock `trust` for local socket and 127.0.0.1/::1 — which is
  precisely why every `docker exec pg_db psql -U postgres` in the doc works without a password.
  Not a live defect (loopback inside the container ≈ docker-group access ≈ root-equivalent), but an
  operator hardening "to the doc" could remove those lines and break every maintenance command, or
  conversely believe password-less exec is a misconfiguration.
- Fix: one sentence in STEP 2 stating the loopback-trust default is retained deliberately and that
  the doc's `docker exec` psql commands rely on it.
